MAINTAINER DECISION (2026-10-24, recorded on #1 and #44):
1. GITHUB IS THE STATE STORE. The local SQLite store is only a cache/outbox/event log rebuilt by `harness sync` (docs/PLAN.md "Mirror to GitHub", "harness sync"). The plan approval must be written to GitHub FIRST (the control issue's harness ledger comment, via the existing ledger/outbox functions) and mirrored into the local store afterwards or rebuilt by `harness sync`. The issue's `record_plan_approval(store, ...)` writing only to the local store is NOT acceptable: make it write the ledger record through the outbox (`harness.github.ledger` render/parse + outbox) and mirror it in the store, and make `harness sync` (harness/sync.py) restore the mirror from the ledger. Add tests for both (record -> ledger snapshot contains plan_sha/approved_by/via; wipe the store -> sync -> `check_plan_approval` still APPROVED).
2. PLAN SOURCE is a repo file OR a GitHub issue. `PlanDoc` gets `kind: Literal["file","issue"]`, `path: str | None`, `issue: int | None`, `ref`, `sha`, `text`, `title`, `headings`. `sha` is the git blob sha for a file and `sha256(title + "\n" + body)` hex for an issue (documented). `load_plan_doc(gh, repo, path=None, issue=None, ref=None)` loads either (exactly one of path/issue required); size cap 500 KB; ETag cached through the existing client cache; 304 path tested.
3. FREEZE = approval bound to the `sha`: the frozen snapshot is stored in the control issue's ledger (plan kind, path/issue, sha, a title, approved_by, via, timestamp; the plan TEXT itself is not copied into the ledger, only the hash, so large plans do not blow the ledger size cap). If the plan's current sha differs from the approved sha the status is `STALE` and the gate reopens (but nothing already created is cancelled).
4. APPROVAL SIGNALS (all end in the SAME ledger record via one function): (a) label `harness:plan-approved` on the control issue (add it to harness/github/labels.py HARNESS_LABELS if absent), (b) for file plans, the PR that last modified the file is merged, (c) a `/harness approve plan` slash command comment through the existing command parser (harness/github/commands.py) if it fits its model; skip (c) with a note if it needs a larger change, (d) `harness plan approve` CLI. Only the repo owner or an allowlisted user counts: reuse the allowlist helper already used by the slash-command parser; unauthorised actors are ignored and reported as PENDING with a note.
5. Everything else per the issue: `request_plan_approval` idempotent per sha (one event comment + label `harness:needs-you`), `harness plan show`/`harness plan approve [--repo --control-issue --path/--issue]` CLI (thin), gate `scope: issue|campaign` on the gate node model (campaign-scoped `plan` gates resolve through `check_plan_approval`; validator/schema updated; regenerate TS types/JSON schema per the drift check and run the web checks), `plan_gate_outcome`, inbox kind `plan_approval` for pending campaign plan gates (check the existing enum and the Inbox code), ledger schema extension backwards compatible (optional field).
6. Tests: all acceptance criteria from the issue with respx; plus the two GitHub-first tests from item 1 and a test that a plan given as an issue goes STALE when the issue body is edited.
7. Rules: no new dependencies; do not touch adapters/, dispatcher, .orchestrator/, .claude/, docs/PLAN.md; pre-existing tests unmodified unless a change is unavoidable (then minimal and listed in the PR body with the reason); no scratch scripts or stray root files; no package.json; no new broad `except Exception`; ruff check + ruff format --check + pytest green (+ `cd web && npm test && npm run lint && npm run typecheck` when TS types change).
