1. The LLM backend protocol is `ReviewBackend` in harness/llm/backend.py (`async review(system, prompt, schema, workdir) -> dict`), with `FakeBackend` (scripted responses; a str is raw text, an Exception is raised) and `ClaudeSdkBackend`. There is no `LLMBackend`. Mirror harness/llm/reviewer.py for prompt rendering (`render_prompt`, `fence`, prompts in harness/llm/prompts/), JSON parsing/validation, retries and redaction; harness/llm/selector.py (merged in #98) is the closest recent example (system prompt + prompt files, fallback, injection fencing). The decomposer must NOT import `claude_agent_sdk` itself.
2. `PlanDoc` exists in harness/planner/plan_doc.py (merged #100: `kind`, `path`, `issue`, `ref`, `sha`, `text`, `title`, `headings`, `source`); import it, do not redefine. `load_plan_doc` is there too.
3. Capability table: agents are `Capabilities` objects (harness/adapters/base.py: plan_approval, messaging, opens_pr, local_workspace, `.names()` -> {"plan","message","pr","local"}); the playbook validator takes `agent_caps: dict[str, set[str]]` (harness/playbook/validate.py) and `AdapterRegistry.caps_by_name()` produces it. For `plan_on_agent_without_plan`, reuse `harness.playbook.validate.validate` on the chosen playbook with `agent_caps` for the proposed agent (the validator already flags a `plan` action on an agent without the `plan` capability when the node's agent is literal) or reuse the same check; do not invent a second capability check. Playbook ids available come from the callers (`playbooks: Collection[str]`), so `validate_proposal` takes `agents: Mapping[str, Capabilities]` and `playbooks: Mapping[str, Playbook] | Collection[str]` (accept the Playbook objects so (playbook, agent) pairs can be validated; with only ids, skip the pair check).
4. Schema/TS generation: scripts/export_playbook_schema.py + web/src/generated/ (playbook.schema.json, playbook.d.ts, ports.cases.json) and the CI drift check (see how `npm run gen:types` and the `--check` flag work). Add `ProposedPlan` JSON Schema as web/src/generated/proposal.schema.json and generate web/src/generated/proposal.d.ts with the same mechanism; keep the drift check green and run the web checks.
5. Repo context: `RepoConfig.context_files` lives in harness/config.py (parsed from `.harness/config.yaml` by `parse_repo_config`); file contents are fetched with `GitHub.file_text(repo, path, ref)`, existing issue titles via `GitHub.issues(...)`. `build_repo_context(gh, repo, config: RepoConfig, ref=None)` caps each file (e.g. 20 KB) and total (e.g. 100 KB) and lists up to 200 existing titles; use respx in tests.
6. The decomposer's output is a PROPOSAL ONLY (`ProposedPlan`); it creates nothing on GitHub. Validation codes exactly as the issue lists them (`duplicate_key`, `unknown_dep`, `self_dep`, `cycle` with the cycle path, `unknown_agent`, `unknown_playbook`, `plan_on_agent_without_plan`, `no_acceptance`, `too_many_issues`, `title_too_long`, `empty_body`); cycle detection iterative and tested on a 500-node chain; `ProposalIssue` is a small dataclass/model (code, key or None, message). `decompose(...)` makes up to 2 repair attempts feeding back the error list, then raises `DecompositionError(issues)`; invalid JSON counts as a failed attempt.

A golden-style test asserts the capability table and the untrusted delimiter are in the rendered prompt, and the injection test asserts `ignore previous instructions` stays inside the fenced block.
