## 4. `harness run <owner/repo> <issue> [--playbook ID] [--agent NAME] [--max-ticks N]`
- `sync_repo` the repo (or at least fetch and cache the issue).
- If a non-terminal run already exists for the issue, CONTINUE it (print `continuing <run id>`) instead of starting a new one; this is how a run resumes after `needs-you` was resolved (e.g. `harness approve`).
- Else resolve: playbook = `--playbook` > the issue's `playbook:<x>` label > `repo_config.default_playbook`; looked up in `.harness/playbooks/<id>.yaml` of the repo (`gh.file_text`, parsed with `load_playbook`; the git blob sha from the contents API is `playbook_sha` if easily available, else None) then in the built-ins; unknown → exit 1 with a one-line error. Agent = `--agent` > `agent:<x>` label > `repo_config.default_agent`; an agent not in the adapter registry → exit 1. Then `start_run`.
- Foreground loop: `await runner.tick()`, `await outbox.drain_once()` (or the outbox's equivalent), print each new event of this run as one line (`events_since`), until the run is terminal or `needs-you` (then print what is needed: the needs-you reason and gate id) or `--max-ticks` is hit. Between ticks sleep `min(5.0, seconds until the earliest poll_after)` via the injected sleep. Exit code 0 for `done` and `needs-you`, 1 for `failed`/`cancelled`.

## 5. Run lock (`harness/lock.py`)
- The lock lives in the control issue's ledger comment (`find_ledger`/`render_ledger`/`parse_ledger` from `ledger.py`), as `snapshot["lock"] = {"host", "pid", "token", "since", "heartbeat"}` (ISO times). Other snapshot keys are preserved.
- `async acquire(gh, repo, control_issue, *, host, pid, now_iso, force=False, stale_after=900) -> Lock`: read the control issue's comments; a lock held by someone else whose `heartbeat` is younger than `stale_after` seconds → raise `LockHeld(holder)` unless `force`. Same host+pid → re-acquire. Write the ledger directly (edit or create the comment; this is synchronous by design, not via the outbox), then re-read and verify the token is ours (else `LockHeld`).
- `async heartbeat(lock, now_iso)`, `async release(lock)` (removes `lock`, keeps other keys).
- Repos without `control_issue`: no lock; the daemon logs a warning event and still runs them.

## 6. `harness daemon [--force-unlock]` (`harness/daemon.py`)
`async run_daemon(app, stop: asyncio.Event, *, host, pid, force_unlock=False, sync_every=300, commands_every=30, heartbeat_every=60, idle=1.0)`:
- Acquire the lock for every registered repo first; `LockHeld` → print the holder and exit 1 (nothing started).
- Then run concurrently until `stop`: `runner.run_forever(stop)`, the outbox drain loop, `poll_commands` per repo every `commands_every`, `sync_repo` per repo every `sync_every`, lock heartbeats every `heartbeat_every`. Exceptions in a periodic job are recorded as events and do not stop the daemon.
- SIGINT/SIGTERM set `stop` (installed by the CLI command with `loop.add_signal_handler`). On stop: wait for the tasks, release the locks, `app.aclose()`.

## 7. `harness runs [--repo R] [--status S]` and `harness show <run>`
`runs`: table of id, issue, playbook, status, active nodes, PR. `show`: run fields, steps (node, visit, status, outcome, a one-line output summary capped at 200 chars, redacted), then the last 50 events. Unknown run → exit 1.

## 8. `docs/RUNBOOK.md`
1. Setup: install (`uv tool install` or `uv run`), env files (`~/.config/jules/env` with mode 600, `GH_TOKEN`/`gh auth token`, `ANTHROPIC_API_KEY` for the reviewer, `uv sync --extra claude`), `harness init <repo>` (labels, control issue), `.harness/config.yaml` example with every field from `RepoConfig`, `.harness/playbooks/` and `.harness/checklists/`.
2. Sandbox end-to-end: create a private sandbox repo; one issue "add `slugify()` with tests" with Scope/Acceptance criteria/Out of scope; `gates: {plan: auto, merge: human}`; `harness run` → plan → review → implement → CI → scope → PR review → `needs-you` at merge; approve via `harness approve <issue>`; repeat with a second issue approved via a `/harness approve` comment under the daemon. Checklist of what to verify: ledger comment content, labels per status, control-table row, merged PR, ticked boxes, issue closed, and kill the daemon mid-run → `harness sync` → restart → no duplicate session, PR or comment.
3. Migrating a repo off the gargi-orchestrator skill: stop the skill (archive Jules sessions), move/adopt the control issue, `harness init`, take the lock with `harness daemon`, never run both on one repo.
4. Troubleshooting: lock held (`--force-unlock`), outbox failures (`harness status`), rate limits.
