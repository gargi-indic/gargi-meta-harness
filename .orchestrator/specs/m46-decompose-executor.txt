MAINTAINER RULE: GITHUB IS THE STATE STORE (SQLite is only a cache/outbox/event log rebuilt by `harness sync`). The issue's local-only `proposals` table is therefore NOT enough. Persist a proposal GitHub-first:
1. `harness/planner/proposal_store.py`: `save_proposal(store, outbox, *, repo, control_issue, run_id, plan_sha, proposal, status="proposed")` writes the proposal to GitHub through the outbox as harness-owned comment(s) on the control issue with the marker `<!-- harness:proposal run=<run_id> sha=<plan_sha> part=<k>/<n> -->` plus the JSON (in a fenced block inside `<details>`), chunked so no comment exceeds ~60 000 characters (GitHub's limit is 65 536), edited in place on re-save (find existing by marker; check what outbox/edit_comment/add_comment ops exist and reuse them; add an op only if unavoidable), AND records a small summary under the `proposal` key of the control issue's ledger via the existing `merge_ledger` outbox op (plan_sha, run_id, issue count, status, comment ids if available, never the full JSON). `get_proposal`/`update_proposal` read/modify through the same path. The local `proposals(id, run_id, plan_sha, json, status, created_at)` table (new migration, M0.4 mechanism) is a MIRROR written only after GitHub accepted the write (see how #100's `merge_ledger` op mirrors the plan record via `ledger_mirror_key`/`meta`), and `harness sync` (harness/sync.py) must rebuild it from the marker comments. Tests: save -> comments contain the marker and valid JSON; wipe the local DB -> sync -> `get_proposal` returns the same proposal; a 40-issue proposal needing more than one comment chunk round-trips; re-saving the same sha edits instead of duplicating.
2. The executor itself stays idempotent: if a proposal for the same `plan_sha` and run already exists (store mirror first, then GitHub), reuse it without calling the LLM again (test: crash after the LLM call before commit, re-advance, backend called once).
