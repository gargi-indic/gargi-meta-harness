1. GitHub is the state store and the outbox is the ONLY path for content writes (docs/PLAN.md "Mirror to GitHub, through a throttled outbox"). The outbox (harness/github/outbox.py) currently has ops add_comment, edit_comment, upsert_ledger, merge_ledger, edit_issue_body, set_labels, merge_pull, delete_branch, close_issue, create_pull, tick_boxes; it has NO create_issue / add_sub_issue / add_blocked_by / ensure_label ops. Creating issues needs the created number/id before the next step (sub-issue attach needs the new issue's numeric ID; dependencies use issue IDs, see `GitHub.add_sub_issue(repo, number, sub_issue_id)` and `add_blocked_by(repo, number, blocker_id)` in harness/github/client.py). Add the minimal new outbox ops (`create_issue`, `add_sub_issue`, `add_blocked_by`, `ensure_label`) following the existing intent-then-ref pattern (read how `create_pull` records its result/ref and how intents are made idempotent after a crash), and give `materialize` a way to await each op's result (for example enqueue, drain via the outbox's own throttled drain, read the recorded ref) WITHOUT bypassing the throttle. The client write methods must not be called from materialize.py itself (test: patch them to fail).

A crash after the issue was created but before its ref was recorded must not duplicate: the marker search recovers it. Sub-issue attach and dependency creation are idempotent (read existing `sub_issues`/`blocked_by` first; re-adding is skipped).
